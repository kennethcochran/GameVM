# Dynamic Loading Specification

## Purpose
Specify the GameVM mechanism for dynamic loading, symbol relocation, and memory management on later-generation (4th–5th Gen) and disk-based platforms that must load code and data into RAM rather than rely only on memory-mapped cartridges. It covers the ELF module format, the runtime loader, overlay management, async loading, symbol resolution, and media-specific optimizations.
Aspirational — not yet implemented.

## Requirements

### Requirement: ELF Module Format
GameVM MUST emit loadable modules as relocatable ELF files ("Minimal ELF" profile) generated by the host and consumed by a minimal runtime loader on the target, using the standard ELF representation of loadable segments, symbol tables, and relocation tables suited to the target's emission format.

#### Scenario: Host emits relocatable ELF
- **WHEN** the host (PC) compiles a module for a dynamic-loading target
- **THEN** it MUST emit a minimal ELF binary mapping LLIR to the target's emission format (STC calls, DTC/ITC address lists, or TTC tokens) with standard ELF relocation entries

#### Scenario: Target ELF loader
- **WHEN** the target runtime loads such an ELF module into RAM
- **THEN** the ELF loader MUST patch addresses in RAM based on the relocation table and bind imports to the global symbol table

### Requirement: Static vs. Dynamic Linking
GameVM MUST support both static linking, where addresses are resolved at build time for the resident kernel, and dynamic linking, where modules are emitted as relocatable ELF files loaded at runtime.

#### Scenario: Static linking for the resident kernel
- **WHEN** the resident kernel is built
- **THEN** its addresses MUST be resolved at build time (static linking)

#### Scenario: Dynamic linking for add-on modules
- **WHEN** a non-resident module is built
- **THEN** it MUST be emitted as a relocatable ELF file whose addresses are resolved at load time (dynamic linking)

### Requirement: ELF Contents Profile
Each GameVM ELF module MUST contain an ELF header, loadable program segments (code and data), a symbol table (`.symtab`) for exported/imported LLIR entities, and relocation tables (`.rel`/`.rela`) that cover the backend's emission forms.

#### Scenario: Relocation for each emission format
- **WHEN** a module's relocations are generated or applied
- **THEN** `STC` MUST relocate native `CALL` targets, DTC/ITC MUST relocate the list of memory addresses, and TTC MUST relocate the token-to-address jump table and data pointers

### Requirement: Runtime Loader Responsibilities
The runtime loader MUST allocate a contiguous block of RAM for the module, read the module from media (CD-ROM, disk, etc.), relocate internal pointers and branches to the actual RAM address, resolve external dependencies against the Resident Module or other loaded modules, and execute module-level constructor/initializers.

#### Scenario: Loading a module
- **WHEN** a module is loaded
- **THEN** the loader MUST find a contiguous free RAM block, read the module from media, patch all internal pointers and branches to its actual address, bind external symbols, and run module-level initialization

### Requirement: Loader Standard Library API
GameVM MUST provide a standard library API for dynamic loading with a module handle, load-status enumeration, synchronous loading, asynchronous loading, unloading, and manual symbol retrieval.

#### Scenario: Synchronous load
- **WHEN** `LoadModule(ModuleName)` is called
- **THEN** it MUST block until the module is loaded and return a module handle, or an error status among file-not-found, out-of-memory, and relocation error

#### Scenario: Asynchronous load and unload
- **WHEN** `LoadModuleAsync` returns immediately and a load is requested, or `UnloadModule(Handle)` is called
- **THEN** the module load MUST invoke the completion callback when finished, and unloading MUST unload the module from memory

#### Scenario: Manual symbol retrieval
- **WHEN** a developer needs a specific export by name
- **THEN** `GetModuleProc(Handle, ProcName)` MUST return a pointer to the requested procedure

### Requirement: Overlay Regions
Developers MUST be able to define overlay regions in project configuration / memory map, where multiple modules share the same memory address and swap in and out of the region as needed.

#### Scenario: Defining overlay regions
- **WHEN** a project memory map declares a region with `"type": "overlay"` (e.g., `LevelOverlay`)
- **THEN** modules assigned to that region MUST share the same base address and be swapped in and out as needed, while a resident region stays in place

### Requirement: Handling Stale Pointers
The runtime MUST handle pointers into a swapped-out overlay, optionally tracking them when "Safe Mode" is enabled, to prevent unsafe access.

#### Scenario: Safe Mode reference protection
- **WHEN** Safe Mode is enabled and an overlay is swapped out
- **THEN** the runtime MUST track references, prevent unloading if active stack frames point into the module, and replace exported function pointers with a fault handler that throws an error or triggers a reload

### Requirement: Overlay Memory Management
The loader MUST be able to unload old overlays to make room for new ones, swapping modules in and out of shared RAM regions.

#### Scenario: Swapping modules
- **WHEN** an overlay region is needed by a new module
- **THEN** the loader MUST unload / swap out the current occupant and map the new module into the same region

### Requirement: Slow-Media Optimization Strategies
For slow media (CD-ROM, disk), the loader MUST support batching, pre-fetching and double buffering to hide seek/latency.

#### Scenario: Loading during play
- **WHEN** game content runs on slow media
- **THEN** modules SHOULD be grouped into contiguous "Load Bundles" to minimize screen CD-ROM seek times, pre-fetched in the background (loading an expected "next" module), and double-buffered so a new level can load while the current one remains active

### Requirement: Resident Module and Global Symbol Table
The first module loaded (Resident Module / kernel) MUST contain the runtime loader, basic HAL, and the global symbol table, and all subsequently loaded modules MUST resolve their imports against that table.

#### Scenario: Import resolution
- **WHEN** a loaded module has unresolved imports
- **THEN** it MUST resolve them against the Resident Module's global symbol table (and other loaded modules)

### Requirement: Lazy Symbol Binding
For 5th-gen platforms GameVM MUST be able to postpone symbol resolution until the first call to a function to speed initial loading.

#### Scenario: Lazy binding
- **WHEN** lambda lazy binding is enabled and a module with unresolved imports is loaded
- **THEN** symbol resolution MUST be deferred until the first call of each function, trading faster initial load for overhead on that first call

### Requirement: Platform-Specific Support
GameVM MUST provide platform-specific dynamic loading behavior for the Sony PlayStation (PS1) and Nintendo 64 (N64).

#### Scenario: PlayStation streaming
- **WHEN** loading dynamic content on the PS1
- **THEN** the runtime MUST use DMA for high-speed CD-ROM to RAM streaming, a compressed relocation table to save space on the disc, and support "Object Overlays" for boss entities

#### Scenario: N64 RAM management
- **WHEN** loading dynamic content on the N64
- **THEN** the runtime MUST use dynamic loading to manage the limited 4MB/8MB RAM, stream code from ROM/RDRAM via high-speed DMA, and allow code to execute from the command/instruction cache after being DMAd

### Requirement: Safety and Determinism
The build system MUST statically verify that worst-case load time does not break frame-rate-critical logic, and the loader MUST avoid heap fragmentation.

#### Scenario: Deterministic load analysis
- **WHEN** games are built with dynamic loading
- **THEN** the build system MUST verify through static analysis that the worst-case load time does not break frame-rate-critical logic, and the loader MUST use a stack-based or region-based allocator to avoid heap fragmentation

### Requirement: Dynamic Module Resolution
GameVM MUST support resolving module names at runtime (e.g., Python's `__import__(name)`) beyond static path resolution, via either a module registry or ELF dispatch.

#### Scenario: Module registry lookup (cartridge targets)
- **WHEN** a dynamic name is resolved on a cartridge target where all modules build into the resident ROM
- **THEN** the runtime MUST look the name up in a static string-to-pointer map via binary search on sorted strings (O(log n)) and return the address of the module's export table / vtable

#### Scenario: ELF dispatch (disk targets)
- **WHEN** a dynamic name is resolved on a disk/slow-media target
- **THEN** the import function MUST map the dynamic string to a file path (e.g., `modules/gfx_vga.elf`), invoke the async ELF loader, and return the module handle once relocation is complete
